# 版本记录：v0.42-platform-closure-and-recommendation-chain

## 1. 本轮目标

本轮要解决的问题，不是继续增加页面，而是把已经建立的行业 taxonomy 真正变成平台化推荐链。

重点目标：

- 让行业 taxonomy 不只服务导航和表单，而是贯穿知识库、案例、方案和诊断
- 在首页首屏补上轻量行业入口层
- 在知识详情页和方案详情页建立自然的相关推荐链
- 让导航中的行业方案更像平台入口，而不是普通下拉列表

本轮属于：

- 结构收口
- 推荐链补全
- 可维护性提升

## 2. 背景与上下文

本轮承接：

- v0.35-industry-taxonomy-unification
- v0.39-risk-card-alignment-closure
- v0.40-hero-risk-panel-final-alignment
- v0.41-hero-risk-panel-width-and-text-closure

v0.35 已经建立了统一行业实体系统，并让行业方案、诊断表单、首页方案顺序开始从 taxonomy 读取。但知识库和案例仍然没有行业感知，导致整站虽然“有行业分类”，却还没有真正形成：

行业入口 → 行业方案 → 行业案例 → 行业知识 → 诊断

这样的完整平台链路。

另外，当前仓库实际结构与任务说明存在差异：

- 知识库数据位于 `src/data/articles.ts`，不是 `src/data/knowledge.ts`
- 案例目前是 `/cases#slug` 的锚点结构，没有单独的 `[slug]` 详情页

因此本轮明确采用“兼容现有结构的增量改造”，不新建复杂页面。

## 3. 问题分析

表面现象：

- 首页已有行业方案，但首屏没有直接行业入口
- 知识详情页只有相关文章，没有指向行业方案和案例
- 方案详情页只有相关方案，没有对应案例
- 导航行业方案下拉只有名称，没有判断语义
- 案例数据和知识库数据都没有行业字段，推荐只能靠手写

核心矛盾：

站点已经有“内容”和“分类”，但没有“跨内容类型的统一行业推荐关系”。

如果不补这一层，网站更像多个模块并排，而不是一个真正的平台系统。

## 4. 候选方案比较

### 方案 A：新增复杂行业页和案例详情页

核心思路：

新建行业聚合页、案例详情页，再通过这些页面承接推荐关系。

优点：

- 结构完整
- 理论上扩展性更强

缺点：

- 改动面大
- 需要新增页面结构和更多导航逻辑
- 超出本轮“最小改动”和“不重构”的范围

放弃原因：

当前仓库已经有锚点式案例结构和稳定页面体系，本轮更适合先把推荐链接通，而不是扩充站点层级。

### 方案 B：基于现有页面补行业字段和统一推荐函数

核心思路：

给文章和案例补 `industries` 字段，再通过统一 helper 在现有页面中输出相关推荐链。

优点：

- 改动小
- 数据驱动
- 兼容当前 URL 和现有组件
- 后续扩展到更多文章和案例时成本低

缺点：

- 仍然依赖当前案例锚点结构
- 推荐逻辑还不是完全独立的内容系统

最终选择原因：

最符合本轮目标和仓库现状，能够用最少改动实现“平台闭环感”。

## 5. 最终决策

最终采用方案 B，并分成四个层面落地：

1. 在行业 taxonomy 中增加 `judgment` 字段，统一承接导航和行业判断语义
2. 在文章与案例数据中增加 `industries` 字段，建立统一行业归属
3. 在 `site-data` 中补 `getRelatedKnowledge`、`getRelatedCases` 等统一推荐函数
4. 在首页、导航、知识详情页、方案详情页中接入轻量行业入口和推荐链

## 6. 具体实现

改动文件如下：

### `lib/industry-taxonomy.ts`

- 为行业实体新增 `judgment`
- 为每个行业补一条简短判断句

作用：

- 导航行业下拉不再只是名称列表
- 后续首页或 CTA 如果要用行业判断语义，也能继续复用

### `src/data/articles.ts`

- 为文章模型增加 `industries?: string[]`
- 增加 `articleIndustryMap`
- 导出 `getArticlesByIndustries()`

作用：

- 知识库文章开始具备行业归属
- 后续知识详情页可以自然推荐行业方案、行业案例和诊断入口

### `src/data/cases.ts`

- 为案例模型增加 `industries?: string[]`
- 给现有四个案例补行业归属
- 导出 `getCasesByIndustries()`

作用：

- 案例不再只是孤立卡片
- 能被行业方案和知识页统一调用

### `lib/site-data.ts`

- 转发 `getArticlesByIndustries` 和 `getCasesByIndustries`
- 新增 `getRelatedKnowledge()`
- 新增 `getRelatedCases()`
- 行业方案导航 children 新增 `description`

作用：

- 保持页面只从站点数据层拿统一数据
- 避免页面自己拼推荐逻辑

### `components/Header.tsx`

- 行业方案下拉升级为“左侧行业名 + 右侧一句判断”
- 保持轻量，不做图片、不做复杂分组

作用：

- 导航更像平台入口，而不是普通栏目

### `app/page.tsx`

- Hero CTA 下新增轻量行业 pills
- 直接从 `getFeaturedIndustries()` 读取

作用：

- 首屏开始出现行业入口层
- 用户能更快判断自己属于哪类实验室

### `components/CaseCard.tsx`

- 压缩描述为单行
- CTA 改为 `查看问题路径`

作用：

- 案例卡更像平台入口
- 信息密度更稳，移动端更利于扫读

### `app/knowledge/[slug]/page.tsx`

- 在正文后新增轻量推荐链：
  - 相关行业方案
  - 相关案例
  - 开始路径诊断

作用：

- 知识详情页从“单页阅读”升级为“行业判断入口”

### `app/solutions/[slug]/page.tsx`

- 在相关行业方案之外，新增相关案例区

作用：

- 方案页不再只推荐别的方案
- 用户可以顺着行业链继续看风险场景

## 7. 本轮优点

- 推荐链终于从行业 taxonomy 出发打通
- 首页、导航、知识、方案、案例之间开始形成统一行业语义
- 保持了现有 URL、不重构页面结构
- 数据逻辑统一沉到数据层，后续扩展新行业和新内容成本更低
- 视觉上依然克制，没有破坏 mobile-first 节奏

## 8. 本轮缺点与代价

- 案例仍然是锚点页，不是独立详情页，推荐链的承接深度有限
- 文章行业映射当前仍是手工维护，需要后续随着内容增长继续整理
- 知识详情页目前的行业方案推荐是按文章 industries 推导出来的轻量实现，还不是更复杂的内容权重系统

这些妥协是当前仓库结构下可接受的，优先保证平台链路形成，而不是在本轮引入新架构。

## 9. 验证与结果

本轮完成后应执行：

- `npm run typecheck`
- `npm run build`
- `npm run dev`

本次代码层面重点关注：

- 新增字段是否保持向下兼容
- 推荐函数在无 industries 时是否有 fallback
- 首页、知识页、方案页是否仍能按原结构渲染

如果本轮 shell 运行环境异常，需要在恢复后补做命令验证。

## 10. 本轮结论

本轮最重要的结论是：

真正的平台感，不是多做几个页面，而是让已有内容之间形成统一的判断链。

只要行业 taxonomy 能贯穿知识、案例、方案和诊断，站点就会从“内容集合”变成“路径平台”。

## 11. 下一轮建议

1. 为案例页补轻量行业筛选或行业分组，让 `/cases` 本身也具备更强的行业入口感
2. 继续清理知识库和 CTA 中残留的非统一措辞，保证全站 CTA 完全收口
3. 如果后续内容继续增长，再考虑是否把案例从锚点结构升级为独立详情页
