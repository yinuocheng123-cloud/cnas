# 版本记录：v0.20-homepage-spacing-tightening

## 1. 本轮目标

本轮目标是在 `v0.19` 的基础上继续收紧首页纵向节奏，把“舒服但松”的页面状态收口到“克制、有密度、有节奏”的状态。

本轮优先级属于：

- 视觉收口
- 可读性优化
- 设计 token 约束加严

## 2. 背景与上下文

本轮承接以下记录：

- `custom/notes/v0.19-homepage-density-refinement.md`
- `custom/notes/v0.13-design-token-system.md`

`v0.19` 已经完成了首屏信息降噪、路径区标签删除、风险提示并入右侧视觉区等动作，但首页 section 之间的垂直留白仍然偏松。尤其是 Hero 之后到“平台路径”、内容区之间到底部 CTA，阅读时仍有明显“断层感”。

本轮不再继续调整标题层级、不改组件结构、不改卡片内容密度，只处理 section 级别 spacing。这一点是为了延续 `v0.13` 的 token 化方向，同时避免为追求紧凑而把卡片内部压得过满。

当前仓库内仍未实际存在根目录 `AGENTS.md` 文件，因此无法把“最新一期路径”回写到仓库内该文件，只能在本轮 notes 中显式保留记录。

## 3. 问题分析

本轮开始前的核心问题不是页面元素过多，而是 section 级留白过大：

1. 全局 `section-space` 仍使用 `40 / 48`，桌面端已超出本轮要求的上限。
2. 首页“平台路径”区仍然使用较大的上下 padding，Hero 结束后视觉上有明显下坠感。
3. 内容区之间虽然结构合理，但区块总高度仍偏长，滚动时容易出现一段内容结束后要再滑一截才进入下一段的感受。
4. 如果直接压缩卡片 padding 或正文行距，虽然也能缩短页面高度，但会损伤内容的呼吸感，不符合本轮“只收紧 section，不挤压内容”的目标。

真正要解决的矛盾是：让 section 之间更连续，而不是让模块内部更拥挤。

## 4. 候选方案比较

### 方案一：全站统一大幅压缩所有 padding

核心思路：把 section、卡片、标题间距一起缩小，快速降低页面总高度。

优点：

- 页面高度下降明显
- 改动集中，视觉变化立刻可见

缺点：

- 会同时压缩卡片内部呼吸感
- 很容易让首页变成“紧但挤”
- 不符合用户本轮“不动内部间距太多”的要求

放弃原因：收益来自“全面压缩”，但副作用太大。

### 方案二：只收紧 section token，并对首页区块单独微调

核心思路：把全局 section 节奏统一收口到 `32 / 40`，再在首页对 Hero 后、内容区之间的上下留白逐段再压一档，但保持卡片内部 spacing 基本不动。

优点：

- 改动边界清晰，符合本轮限制
- 可以保留原有内容呼吸感
- 首页会更紧凑，但不会出现“所有间距都一样”的机械感

缺点：

- 变化主要体现在整体节奏，需要结合页面通读才能感知价值
- 其他页面也会跟着使用更紧的全局 section token，虽然风险较低，但仍属于轻度全站影响

最终选择原因：最符合本轮目标，也最符合最小改动原则。

## 5. 最终决策

本轮最终采用“全局 token 收紧 + 首页分段微调”的方案：

1. 在 `app/globals.css` 中把 spacing token 锁定为 `8 / 16 / 24 / 32 / 40`
2. 把全局 `section-space` 从 `40 / 48` 收紧到 `32 / 40`
3. 在首页单独压缩：
   - Hero → 平台路径
   - 平台路径 → 热门问题 / 内容区
   - 内容区 → 底部 CTA 之前的 section 高度
4. 保持卡片内部 padding、正文行距和现有组件结构不动

## 6. 具体实现

本轮修改文件如下：

- `app/globals.css`
  - 删除 `48px` 对应的 spacing 变量
  - 将 spacing token 明确为 `--space-1` 到 `--space-5`
  - 将 `.section-space` 从 `py-10 md:py-12` 调整为 `py-8 md:py-10`

- `app/page.tsx`
  - 将“平台路径”区调整为 `pt-6 pb-8 md:pt-8 md:pb-8`
  - 将“热门问题入口”“内容分类入口”“行业方案入口”“案例解析”区改为更紧的首页专用 `py-8`
  - 将“风险诊断 + 流程”区保持略高一级的 `py-8 md:py-10`，保留该区块相对更高的权重

## 7. 本轮优点

当前方案带来的正向效果：

- 首页 section 之间的断层感明显减弱
- 首屏以下可以更快进入下一模块，滚动节奏更连续
- 通过只收紧外部留白，保住了卡片内部可读性
- spacing 使用被进一步锁定，后续新增页面更不容易重新出现随意数值

## 8. 本轮缺点与代价

本轮也有明确代价：

- 这是基于代码层的节奏收口，没有做截图级逐像素对照，因此“高级感”的判断仍然依赖真实浏览器观感
- 全局 `section-space` 收紧会轻度影响其他使用该 token 的页面，虽然风险较小，但不是零影响
- 底部 CTA 本身的内部 padding 本轮没有动，因此“内容区 → CTA”的紧凑感主要依赖上一 section 收短，而不是 CTA 自身更薄

这些代价是本轮有意接受的，因为本轮边界就是“不改组件结构，不挤内部内容”。

## 10. 本轮结论

本轮最重要的结论有三点：

1. 首页想要更“贵”，关键不在于再加设计，而在于 section 级节奏是否收得足够稳。
2. 把外部留白压缩到 `32 / 40`，比继续压卡片内部 padding 更安全，也更符合专业内容平台的气质。
3. 首页不需要所有区块用同一节奏，保留“风险诊断区略重、其他内容区略轻”的层级，观感会比机械统一更成熟。

## 11. 下一轮建议

1. 用真实浏览器截图复核首页首屏以下是否已经达到“一屏可见 1.5–2 个模块”的目标。
2. 若继续收口，优先检查 `CtaBlock` 是否需要提供可配置的 section padding，但这应作为单独一轮进行，避免本轮越界。
3. 如果后续继续统一密度，可顺带检查 `/knowledge`、`/solutions`、`/services` 是否也存在 section 级留白偏松的问题。
