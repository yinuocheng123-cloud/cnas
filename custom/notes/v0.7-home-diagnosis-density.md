# 版本记录：v0.7-home-diagnosis-density

## 1. 本轮目标

本轮目标是根据页面截图反馈，增强首页“企业是否适合现在启动CNAS认可？”区块的信息密度，并让下方五步流程更饱满、更有实战判断感。

目标类型：内容表达优化、组件能力增强、转化区体验收口。

## 2. 背景与上下文

本轮承接 `custom/notes/v0.6-production-readiness.md`。上一轮已完成上线前自检、CNAS用词统一、README更新和本地提交。本轮不改变全站架构、不新增路由、不引入后台或数据库，只针对首页诊断入口和诊断页同类步骤组件做局部优化。

## 3. 问题分析

截图中的上方诊断说明虽然方向正确，但每条判断偏短，实战信息不足。下方流程卡片只有步骤名，用户能看懂顺序，但很难判断每一步实际要做什么、为什么要做、会影响哪些评审风险。

核心矛盾是：页面已经具备“诊断入口”，但还不够像企业启动前会真正使用的判断工具。

## 4. 候选方案比较

方案一：只增加文案长度，不改组件。

优点是改动最小。缺点是流程卡片仍然只有标题，无法体现实战路径，因此放弃。

方案二：让步骤组件兼容标题和说明，同时保留字符串用法。

优点是既能增强首页和诊断页，又不破坏其他页面已存在的简单步骤调用。缺点是组件类型略微复杂，需要兼容 `string` 和对象两种数据形态。最终选择该方案。

## 5. 最终决策

保留现有 `ProcessSteps` 组件名称和调用边界，将 `steps` 从单一字符串数组扩展为可接受字符串或 `{ title, description }` 对象。首页使用带说明的步骤对象，诊断页同步使用同类结构，其它页面如果继续传字符串也能兼容。

## 6. 具体实现

修改 `components/ProcessSteps.tsx`：新增 `ProcessStep` 类型，卡片增加最小高度、说明文字和更稳定的间距。

修改 `app/page.tsx`：增强风险诊断区四条判断文案，使其更接近实际 CNAS认可启动前诊断场景，并为五步流程增加实战注解。

修改 `app/diagnosis/page.tsx`：同步增强启动前条件检查步骤，使诊断页与首页入口表达一致。

## 7. 本轮优点

首页诊断区更像“启动前判断工具”，不只是概念说明。流程卡片能够解释每一步要核查的内容，增强了TEO表达中的风险提示、判断清单和流程说明。

## 8. 本轮缺点与代价

流程组件变得稍复杂，但仍保持向后兼容。当前只是静态内容增强，还没有表单、评分、问卷或真实诊断结果输出。

## 9. 验证与结果

本轮计划执行 `npm run typecheck` 和 `npm run build`，并检查首页本地访问状态。若验证通过，说明组件类型和页面渲染未被破坏。

## 10. 本轮结论

在不改变架构的前提下，增强首页风险诊断入口和流程步骤注解，是提升平台专业感与转化质量的低风险改动。

## 11. 下一轮建议

第一，后续可将 `/diagnosis` 做成分层问答式静态诊断页。

第二，可把步骤说明沉淀为数据结构，供首页、诊断页和服务页复用。

第三，上线前可补一次移动端截图检查，确认新增说明不会造成卡片过高或拥挤。
