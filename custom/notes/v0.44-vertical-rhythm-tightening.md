# 版本记录：v0.44-vertical-rhythm-tightening

## 1. 本轮目标

本轮目标是对整站做一次纵向节奏收口，解决栏目之间留白过大、页面像 PPT 分段、滑动断层明显的问题。

本轮属于视觉节奏与可上线体验优化，不新增功能、不调整页面结构、不改内容逻辑，只压缩 section 间距、模块间距、标题说明间距、卡片内边距和列表 gap。

## 2. 背景与上下文

本轮承接以下记录：

- `custom/notes/v0.43-mobile-homepage-simplification.md`
- `custom/notes/v0.42-hero-risk-matrix-restoration.md`
- `custom/notes/v0.41-hero-risk-panel-width-and-text-closure.md`
- `custom/notes/v0.40-hero-risk-panel-final-alignment.md`
- `custom/notes/v0.35-industry-taxonomy-unification.md`

历史结论是：移动端首页已经被简化为决策型路径，PC 端首页保留 Hero 风险矩阵、行业 taxonomy、新能源 / 储能入口与完整内容体系。因此本轮不能重新组织首页模块，也不能破坏 Hero 风险矩阵，只能做节奏收口。

## 3. 问题分析

修改前主要问题集中在三类：

1. 公共 `section-space` 偏松，很多页面继承了 `py-10 md:py-16` 的节奏，导致模块之间像单独幻灯片。
2. 首页多个显式区块使用 `py-10 md:py-16`，PC 端滚动时模块之间断层明显。
3. 部分文章页、方案详情页和 CTA 使用 `md:py-12` 或 `mt-8`，移动端也会显得分段过重。

核心矛盾不是内容太多，而是垂直留白与卡片密度没有统一到产品页节奏。

## 4. 候选方案比较

方案一：逐页单独压缩。

- 优点：每个页面可精细控制。
- 缺点：容易形成新的不一致，后续新增页面仍会继承旧节奏。
- 结论：只作为补充，不作为主方案。

方案二：先收公共 token，再处理显式大间距。

- 优点：影响范围统一，后续页面天然继承更紧凑节奏。
- 缺点：公共卡片 padding 收紧会影响全站卡片，需要验证是否过挤。
- 结论：本轮采用。

方案三：把所有间距压到极小。

- 优点：能快速减少页面长度。
- 缺点：会破坏专业、克制、可信的阅读感。
- 结论：放弃。保留必要呼吸感。

## 5. 最终决策

最终采用“公共 token 收紧 + 核心页面显式间距收口”的方式：

- `section-space` 从 `py-10 md:py-16` 收为 `py-6 md:py-10`。
- 全站卡片从 `md:p-6` 收为 `md:p-5`，移动端保持 `p-4`。
- 首页 PC 区块从 `py-10 md:py-16` 收为 `py-8 md:py-10`。
- 首页移动端模块从 `py/pb-8` 收为 `py/pb-6`。
- CTA 从 `py-8 md:py-12` 收为 `py-6 md:py-10`。
- Footer 桌面端从 `md:py-10` 收为 `md:py-8`。

## 6. 具体实现

本轮修改文件：

- `app/globals.css`：收紧 `section-space`、`.card`、`.card-link` 公共 token。
- `components/HeroSection.tsx`：收紧 Hero 默认和 balanced 垂直 padding，压缩默认按钮区间距。
- `components/RiskEntryCard.tsx`：降低风险四宫格最小高度，减少摘要上间距。
- `components/CtaBlock.tsx`：压缩 CTA 上下 padding。
- `components/Footer.tsx`：压缩 Footer 桌面端上下 padding。
- `app/page.tsx`：压缩移动端首页 6 段之间的间距，压缩 PC 端各模块显式 padding 与底部 CTA 前分隔间距。
- `app/solutions/page.tsx`：压缩方案列表页主体 section。
- `app/cases/page.tsx`：压缩案例页主体 section。
- `app/diagnosis/page.tsx`：压缩诊断页风险原因区底部间距。
- `app/knowledge/[slug]/page.tsx`：压缩文章页头部、正文、判断清单、FAQ、相关推荐之间的间距。
- `app/solutions/[slug]/page.tsx`：压缩方案详情页主体区块间距。
- `app/tags/[tag]/page.tsx`：压缩标签聚合页主体间距。
- `app/services/page.tsx`：压缩服务列表与标题之间的距离。
- `app/admin/leads/page.tsx`：压缩后台线索表格与标题之间的距离，避免全站扫描残留大间距。

## 7. 本轮优点

当前方案让全站节奏更连续：

- 移动端 section 主要落在 `py-6 / py-8`。
- 桌面端 section 主要落在 `md:py-10`，没有继续依赖大面积空白撑高级感。
- 首页从 Hero 到 CTA 的模块衔接更紧凑。
- 卡片列表 gap 保持在 `gap-3 / gap-4` 为主，信息密度更接近产品页。
- 公共 token 被收紧，后续新增页面更容易继承统一节奏。

## 8. 本轮缺点与代价

本轮没有做逐页面视觉截图精修，只做统一节奏收口与核心页面验证。因此：

- 个别长文本卡片在桌面端可能仍需要后续微调高度。
- 公共卡片 `md:p-5` 比之前更紧凑，若后续添加更长内容，需要控制文案长度。
- 本轮没有重新设计任何页面，因此只能解决“太松散”的问题，不解决内容本身复杂度。

## 9. 验证与结果

已完成验证：

- `npm run typecheck`：通过。
- `npm run build`：通过，Next.js 成功生成 87 个静态页面。
- `npm run dev`：本地已有 dev 服务监听 `http://127.0.0.1:3000/`，修改后核心页面可访问。
- HTTP 检查：`/`、`/solutions`、`/cases`、`/diagnosis`、`/knowledge` 均返回 200。

浏览器自动化检查尝试连接本地首页时超时，因此本轮没有留下截图级视觉记录。基于构建结果和 200 检查，确认路由与服务状态正常；视觉层面仍建议后续用真实手机或浏览器做一次截图复核。

## 10. 本轮结论

全站纵向节奏应该优先由公共 token 控制，再由页面显式 class 做少量补充。这样比逐页随机压缩更稳定，也更利于后续继续扩展 CNAS 知识库、方案页和诊断页。

## 11. 下一轮建议

1. 用真实手机浏览器检查首页首屏和移动端 CTA 是否仍然足够靠前。
2. 继续检查文章详情页长文本段落的阅读密度，必要时再做正文行距和段落间距微调。
3. 若后续要上线，可对 `/solutions/[slug]` 和 `/knowledge/[slug]` 做一次截图级视觉复核。
