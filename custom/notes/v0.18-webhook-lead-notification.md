# 版本记录：v0.18-webhook-lead-notification

## 1. 本轮目标

本轮目标是把诊断页线索提交从“本地可收集”升级到“可实时通知”的正式上线版本，同时保留本地存储作为兜底备份。

本轮优先级属于：

- 功能补充
- 上线闭环增强
- 可运营性提升

## 2. 背景与上下文

本轮承接以下记录：

- `custom/notes/v0.17-launch-checklist.md`
- `custom/notes/v0.16-diagnosis-conversion-enhancement.md`

`v0.17` 已经打通了表单提交、本地存储、后台查看和统计埋点，但线索到达后仍需要人工去后台查看，缺少实时通知。  
对于当前阶段的项目目标，“能正式上线”不仅意味着页面可访问，更意味着用户提交后，咨询承接方能够立刻收到通知。

当前仓库中依然没有实际存在的根目录 `AGENTS.md` 文件，因此无法把“最新一期路径”回写到仓库内该文件，只能在 notes 中显式保留本轮记录。

## 3. 问题分析

本轮的核心问题有三个：

1. 线索通知仍然滞后  
   用户提交后虽然会写入 `data/leads.json`，但不会主动提醒，线索需要人工轮询后台。

2. 上一轮 webhook 只是预留，没有明确通道拆分  
   之前只有单个 `LEAD_WEBHOOK_URL` 的占位思路，没有按飞书和企业微信分别封装消息格式与环境变量。

3. 需要兼顾实时性与稳妥性  
   如果只依赖 webhook，外部机器人异常时会丢失线索；如果只保留本地 JSON，又无法做到实时通知。

真正的矛盾不是“怎么发通知”，而是“既要实时，又不能因为通知失败影响主流程”。

## 4. 候选方案比较

### 方案一：先发 webhook，失败再写本地

核心思路：把 webhook 当主存储渠道，本地 JSON 作为失败后的补救。

优点：

- 逻辑表面上更像“实时通知优先”

缺点：

- 如果 webhook 调用超时，主流程会更脆弱
- 线索的最稳妥落点反而被放到后面
- 不符合本轮“本地保留为 fallback”的稳妥要求

最终放弃原因：线索数据应先稳妥落地，再做外部通知。

### 方案二：先写本地，再并行发飞书和企业微信

核心思路：API 校验通过后立即写入本地 `leads.json`，再用并行 webhook 做实时通知，任一 webhook 失败都只记日志，不影响用户成功。

优点：

- 数据先落地，最稳妥
- 飞书和企业微信可同时通知
- 任一 webhook 失败都不会影响用户提交体验
- 与现有 `/admin/leads` 后台形成自然兜底

缺点：

- 本地 JSON 仍然不是长期最优持久化方案
- 仍需部署环境具备可写磁盘，或下一轮升级存储

最终选择原因：最符合当前阶段“正式上线可用”的目标。

## 5. 最终决策

本轮最终采用以下策略：

1. 保留本地 `data/leads.json` 写入逻辑作为先落地、后通知的稳定基线
2. 新增 `lib/webhook.ts`，分开封装飞书和企业微信 webhook
3. 用 `LEAD_WEBHOOK_FEISHU` 与 `LEAD_WEBHOOK_WECHAT` 两个环境变量分别控制通知通道
4. `/api/lead` 提交顺序固定为：
   - 字段校验
   - 写入本地 JSON
   - `Promise.all` 并行发送双 webhook
   - 返回成功
5. 任何 webhook 失败都只 `console.error`，不打断用户提交流程
6. 提交成功后的前端文案改为更有信任感的表达

## 6. 具体实现

本轮主要改动如下：

  - 把 `SITE_URL` 的说明更新为环境变量方式，避免继续误导到旧硬编码域名

## 7. 本轮优点

本轮带来的主要收益有：

- 用户提交后可实时通知咨询承接方
- 飞书和企业微信双通道并行，降低单点通知失败风险
- 本地 JSON 仍保留，后台查看链路无需改变
- 前端成功提示更像真实提交完成，而不是纯技术性“成功”
- README 里已经把运维配置步骤补齐，更接近正式交接文档

## 8. 本轮缺点与代价

本轮仍有以下已知限制：

- 本地 JSON 依然只是当前阶段兜底方案，不适合高并发或无持久磁盘部署
- webhook 成功与否目前只记录日志，没有二次重试队列
- README 中给出了测试方法，但真实飞书/企业微信是否收到消息仍依赖部署环境填入正确 webhook 地址

这些限制是本轮可接受的，因为当前目标是先把正式上线所需的通知闭环打通。

## 10. 本轮结论

本轮最重要的结论有三点：

1. 对当前项目最稳妥的正式上线策略是“本地先落地，webhook 做实时通知”，而不是二选一
2. 飞书和企业微信群机器人都适合当前阶段，因为它们足够轻量，不需要额外鉴权流程
3. README 里的运维说明同样属于正式产物，否则后续即使代码可用，也容易卡在配置和联调阶段

## 11. 下一轮建议

1. 在真实部署环境中填入正式 `LEAD_WEBHOOK_FEISHU` 和 `LEAD_WEBHOOK_WECHAT`，再做一次线上提交通知验证
2. 如果后续线索量增加，优先补 webhook 失败重试或异步队列，而不是先做复杂后台
3. 如果部署平台不提供持久磁盘，下一轮应优先把本地 JSON 兜底升级到数据库或稳定外部存储
