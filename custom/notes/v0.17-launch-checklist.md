# 版本记录：v0.17-launch-checklist

## 1. 本轮目标

本轮目标是补齐项目进入上线前的最后一段闭环能力，让站点从“可浏览”变成“可接线索、可查看、可统计、可联调”。

本轮优先级属于：

- 功能补充
- 上线闭环
- 可运营性提升

## 2. 背景与上下文

本轮承接以下记录：

- `custom/notes/v0.16-diagnosis-conversion-enhancement.md`
- `custom/notes/v0.15-conversion-content-batch.md`

`v0.16` 已经把首页与诊断页的转化表达收紧到更接近咨询入口的形态，但当时诊断页仍是前端承接骨架，没有真实提交链路，也没有线索查看入口与统计注入。  
本轮的任务不是继续做内容量，而是把“有人来 -> 愿意填 -> 能提交 -> 有人接”打通。

当前仓库中没有实际存在的根目录 `AGENTS.md` 文件，因此无法按用户消息中的要求把“最新一期路径”回写到仓库内该文件，只能在本记录中显式保留本轮路径。

## 3. 问题分析

本轮开始前，项目存在四个真实上线缺口：

1. 诊断表单没有后端接收链路  
   用户即使填写了表单，也不会真正进入可跟进状态。

2. 没有基础线索查看能力  
   即使后续接入提交，运营侧也没有轻量后台入口快速查看。

3. 统计未接入  
   上线后无法知道用户是否点击了首页 CTA、是否完成了第一步、是否真正提交了表单。

4. 后台保护存在不稳定风险  
   初始实现使用了 `forbidden()`，但没有启用 Next.js 的 `experimental.authInterrupts`，导致无 `key` 访问 `/admin/leads` 返回 500，而不是预期的 403。

核心矛盾不是“功能少”，而是“转化链路没有形成真实业务闭环”。

## 4. 候选方案比较

### 方案一：直接接数据库或 CMS

核心思路：把线索表单直接接到 Prisma / PostgreSQL 或引入外部 CMS。

优点：

- 更接近长期正式架构
- 数据持久化能力更强

缺点：

- 明显超出本轮“最轻量可用”的范围
- 会牵扯数据库配置、迁移、环境变量与部署策略
- 不符合用户“当前阶段不接复杂数据库”的限制

最终放弃原因：当前阶段目标是先能用，不是一次性走到长期架构。

### 方案二：API Route + 本地 JSON 存储 + 轻量后台

核心思路：用 `/api/lead` 接 JSON 表单，写入 `data/leads.json`，再用 `/admin/leads?key=...` 做只读查看。

优点：

- 改动面小
- 实现快，验证清晰
- 与现有 Next.js App Router 结构兼容
- 能立即形成“提交 -> 存储 -> 查看”的闭环

缺点：

- 本地 JSON 不适合作为长期线上持久化方案
- 在无持久磁盘或 serverless 场景下存在丢数据风险

最终选择原因：最符合本轮“优先能接单”的要求。

## 5. 最终决策

本轮最终采用以下策略：

1. 新增 `/api/lead`，接收诊断表单 JSON 并写入 `data/leads.json`
2. 抽离 `lib/lead-storage.ts` 统一管理线索读写
3. 把诊断页静态表单替换为可提交的 `LeadCaptureForm`
4. 新增 `/admin/leads` 只读后台，通过 `ADMIN_KEY` 查询参数保护
5. 在全局布局中注入 Google Analytics 脚本与轻量事件桥接
6. 用 `SITE_URL` 统一 canonical、OG、robots 与 sitemap 的域名来源
7. 启用 `experimental.authInterrupts`，让后台未授权访问返回稳定 403

## 7. 本轮优点

本轮方案的主要优点有：

- 站点已经具备最小可用的真实获客能力
- 表单提交、存储、查看形成闭环
- 不需要新增数据库或重型后台
- 诊断页转化逻辑与内容策略保持一致，没有破坏设计系统
- 埋点已经接入，可以观察关键行动节点
- 后台保护从异常 500 修复为稳定 403，避免上线后暴露错误页

## 8. 本轮缺点与代价

本轮依然存在以下已知限制：

- `data/leads.json` 适合本地或有持久磁盘的轻量部署，不适合长期 serverless 持久化
- 目前后台没有登录系统，只是查询参数级别保护
- webhook 仅做了接口预留，尚未真正接到企业微信或飞书
- 统计目前只做了基础 GA 注入与关键事件埋点，没有事件看板或转化漏斗报表

这些限制是本轮有意接受的妥协，目的是优先完成“轻量可用”。

## 10. 本轮结论

本轮最重要的结论有三点：

1. 当前阶段最合适的上线闭环方案不是补重型基础设施，而是优先打通轻量提交链路
2. `forbidden()` 这类能力虽然可用，但必须结合 Next.js 的实验开关，否则会把预期的权限拒绝变成 500
3. 对当前项目而言，线索提交通路、后台可见性和统计埋点，比继续补内容数量更接近真正的上线能力

## 11. 下一轮建议

1. 优先把 `LEAD_WEBHOOK_URL` 真正接到企业微信、飞书或邮件通知，提高线索跟进时效
2. 评估部署环境是否具备持久磁盘；如果没有，下一轮应优先把线索存储从 JSON 升级到数据库或稳定外部服务
3. 在统计平台中建立首页 CTA、第一步完成、最终提交三段漏斗，观察真实转化损耗点
