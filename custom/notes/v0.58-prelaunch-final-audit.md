# 版本记录：v0.58-prelaunch-final-audit

## 1. 本轮目标

本轮目标是在准备上线前，对当前站点做一次最终上线检查，判断还有哪些必须调整、建议补充和可以上线后再处理的事项。

本轮属于上线前只读审计与风险分级，不做视觉改版，不新增业务功能，不直接推送仓库。

## 2. 背景与上下文

本轮承接 `v0.56-production-launch-audit` 与 `v0.57-production-hardening`。

`v0.56` 已确认站点具备上线试运行基础，但存在正式域名、依赖安全、线索持久化和日志隐私风险。`v0.57` 已经在本地做了生产化收口，包括线索字段补齐、日志脱敏、robots 屏蔽后台/API/data、README 上线环境变量说明和部署源边界整理。

本轮检查发现这些收口改动仍处于本地未提交状态。如果实际部署平台从 GitHub 仓库拉取代码，那么未提交、未推送的加固不会进入线上版本。

## 3. 问题分析

当前上线风险主要分为四类：

1. 版本发布风险：本地存在未提交改动，包括 `.gitignore`、README、线索 API、表单、SEO、robots、webhook 和版本记录。如果直接从 GitHub 部署，线上可能仍是旧版本。
2. 生产配置风险：未配置 `SITE_URL` 时，生产构建会回退到 `http://localhost:3000`，导致 canonical、Open Graph、sitemap 和 robots 指向本地域名。
3. 线索闭环风险：线索仍写入 `data/leads.json`，该文件适合本地兜底，不适合 serverless 或多实例生产主存储；同时 `data/leads.json` 已经是 Git 跟踪文件，单靠 `.gitignore` 不会让它自动退出版本控制。
4. 构建与工程边界风险：`npm run build` 通过，但 Next.js 提示上级目录存在另一个 `package-lock.json`，导致 workspace root 推断可能不准确；`npm run typecheck` 在没有先生成 `.next/types` 时会失败。

## 4. 候选方案比较

方案一：立刻按当前 GitHub 仓库部署。

- 优点：最快。
- 缺点：如果 v0.57 本地改动没有提交和推送，上线版本会缺少生产化收口。
- 结论：不建议。

方案二：先完成最小上线收口，再部署。

- 优点：能保证正式域名、线索通知、隐私日志、robots 和部署文件边界进入线上。
- 缺点：需要先确认环境变量、提交范围和部署平台。
- 结论：建议采用。

方案三：上线前接入完整数据库和后台。

- 优点：线索持久化更可靠。
- 缺点：上线前引入数据库、权限和迁移变量，风险高于收益。
- 结论：建议上线后迭代，不作为本轮上线阻断。

## 5. 最终决策

当前站点页面构建已经可用，但上线前必须先做最小收口：

- 确认并配置真实 `SITE_URL`。
- 配置 `ADMIN_KEY` 和至少一个线索 webhook。
- 确认本地 v0.57 加固改动是否提交并推送到部署分支。
- 处理已经被 Git 跟踪的本地线索文件和实验日志，避免真实线索或本地日志进入部署源。
- 处理 Next.js workspace root 警告，避免部署追踪范围异常。

## 7. 本轮优点

- `npm run build` 通过，成功生成 87 个页面。
- 构建后的首页 HTML 中文内容、标题、导航、正文均正常，不存在实际页面乱码。
- 生产日志已经改为线索脱敏记录。
- robots 已增加 `/admin`、`/api`、`/data` 屏蔽。
- 表单字段已补齐称呼、企业、电话、微信、需求、来源页面和 UTM。
- 未发现 `.env` 文件被 Git 跟踪。

## 8. 本轮缺点与代价

- `npm run typecheck` 在未先执行 `next build` 生成 `.next/types` 时失败，这是当前检查脚本的可重复性问题。
- `npm audit --omit=dev` 仍有 2 个 moderate 漏洞，来源是 Next.js 依赖链里的 PostCSS，npm 建议的 `--force` 会带来破坏性版本变化。
- `SITE_URL` 未配置时，构建输出会使用 localhost 作为 canonical 和 Open Graph URL。
- `data/leads.json` 与 `custom/experiments/dev-image-system.out.log` 已经被 Git 跟踪，`.gitignore` 只能防止新文件，不能自动取消已跟踪文件。
- 后台使用 query key 访问，适合临时轻量查看，不适合长期生产后台。

## 9. 验证与结果

已执行：

- `git pull --ff-only`：仓库已是最新。
- `git status --short`：存在多处未提交改动。
- `npm run typecheck`：失败，原因是 `.next/types/**/*.ts` include 匹配到缺失文件。
- `npm run build`：通过，生成 87 个页面。
- `npm audit --omit=dev`：仍有 2 个 moderate。
- 构建产物首页 HTML 抽检：中文正文、导航、SEO title/description 正常。
- `git ls-files data/leads.json custom/experiments/dev-image-system.out.log`：两个文件仍被 Git 跟踪。
- `git ls-files .env .env.local .env.production`：未发现环境变量文件被跟踪。

## 10. 本轮结论

当前站点已经接近可上线试运行，但不建议在未确认提交范围、生产环境变量和线索接收方式前直接上线。

最重要的新结论是：`v0.57` 的生产化收口目前看起来仍在本地工作区中，如果部署依赖 GitHub 分支，必须先由用户确认后再提交并推送，否则线上不会包含这些加固。

## 11. 下一轮建议

1. 先确认正式域名、部署平台和部署分支，并配置 `SITE_URL`、`ADMIN_KEY`、至少一个线索 webhook。
2. 用户确认后，把 v0.57/v0.58 相关上线收口改动提交并推送；推送前应先确认是否需要把 `data/leads.json` 和本地实验日志移出 Git 跟踪。
3. 上线后第一天重点观察表单提交成功率、webhook 到达率、404/500、sitemap/robots 输出和搜索引擎抓取情况。
