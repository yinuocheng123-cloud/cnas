# 版本记录：v0.13-design-token-system

## 1. 本轮目标

本轮目标是建立整站统一的设计 Token 规范，把现有“克制、专业、可信”的视觉方向沉淀为可复用的字体、颜色、间距、卡片与按钮体系。

本轮目标属于可维护性提升与视觉系统收口，不改变页面信息架构，不新增复杂功能，不调整导航结构。

## 2. 背景与上下文

本轮承接 `custom/notes/v0.12-visual-hierarchy-closure.md`。上一轮已经弱化导航、统一卡片权重、降低品牌露出和装饰感。本轮继续把这些单点样式沉淀为 Tailwind 主题 Token 与通用组件类，避免后续页面继续自由定义字号、颜色和阴影。

当前项目是 CNAS 专业知识与认可解决方案平台，视觉目标不是营销官网，而是内容型、判断型、转化型专业平台。因此设计系统需要服务阅读效率、信息分层和长期扩展。

## 3. 问题分析

修改前主要问题不是单个页面难看，而是样式来源分散：部分页面使用 `text-sm`、`text-xl`、蓝色硬编码、局部卡片阴影和任意宽度。短期看影响不大，但长期新增文章、分类页和解决方案页时，容易再次变成每个页面各写一套视觉规则。

核心矛盾是：页面需要保持专业克制，但内容模块越来越多，如果没有 Token 约束，后续扩展会导致字号、颜色、间距和按钮层级失控。

## 4. 候选方案比较

方案一：逐页替换全部 Tailwind 类。

优点是控制细，能一次看到每个页面的具体效果。缺点是改动分散，后续复用能力弱，也容易遗漏新增组件。因此没有作为主方案。

方案二：在 Tailwind 与全局样式中建立 Token，再把核心组件迁移到 Token。

优点是影响面集中，后续新增页面可以复用 `site-shell`、`section-space`、`card`、`btn-primary`、`text-copy` 等通用类。缺点是少量页面仍需要人工审查语义是否合适。本轮选择该方案。

## 5. 最终决策

最终采用“Tailwind 主题 Token + 全局组件类 + 核心组件迁移”的方式：

- 字体统一为 `display`、`title`、`body`、`meta` 四档。
- 颜色统一为 `primary`、`ink`、`muted`、`subtle`、`line`、`paper`、`surface`、`card`。
- 卡片统一使用轻边框、白底、极弱阴影。
- 按钮统一为深色主按钮与弱化副按钮。
- 页面容器统一使用 `site-shell`，模块间距使用 `section-space`。

## 6. 具体实现

修改 `tailwind.config.ts`：增加字体、颜色、阴影 Token，并保留少量历史别名以兼容已有实现。

修改 `app/globals.css`：建立全局正文基线和复用组件类，包括 `site-shell`、`section-space`、`card`、`card-link`、`btn-primary`、`btn-secondary`、`text-heading`、`text-copy`、`text-meta-token`。

修改核心组件：`Header`、`SiteHeader`、`HeroSection`、`SectionTitle`、`ArticleCard`、`CategoryCard`、`SolutionCard`、`CaseCard`、`ServiceCard`、`FaqBlock`、`ChecklistBlock`、`CtaBlock`、`Breadcrumb`、`ProcessSteps`、`RiskNotice`、`ArticleList`、`TagList`、`Footer`。

修改主要页面：`app/page.tsx`、`app/knowledge/page.tsx`、`app/knowledge/[slug]/page.tsx`、`app/cnas-process/page.tsx`、`app/diagnosis/page.tsx`、`app/solutions/page.tsx`、`app/solutions/[slug]/page.tsx`、`app/cases/page.tsx`、`app/services/page.tsx`、`app/about/page.tsx`。

## 7. 本轮优点

整站视觉规则更稳定，新增内容页面时可以直接复用 Token，不需要重新判断字号、颜色、间距和卡片风格。

导航、按钮和卡片的权重进一步降低，内容判断、风险提示和流程信息成为页面主体，更符合 CNAS 专业内容平台的定位。

通过扫描清理了自由字号、重阴影、蓝色硬编码、渐变与任意宽度/行高等明显不统一写法。

## 8. 本轮缺点与代价

本轮主要是系统性样式收口，没有进行逐页截图级微调。Token 统一后，个别页面的局部视觉可能比原来更克制，需要后续结合真实浏览器截图继续微调内容密度。

`hero-subline` 使用相对字号形成首页标题第二行层级，它仍依附 H1 字体体系，不作为独立自由字号，但后续若继续严格化，可以把它固化为专门的 Tailwind 插件类或组件变体。

## 9. 验证与结果

本轮执行了样式扫描，确认 `app` 与 `components` 下未发现明显游离 Token 的字体类、重阴影、蓝色硬编码、渐变或任意宽度/行高。

需要继续执行 `npm run typecheck` 与 `npm run build`，确认类型与构建通过。

## 10. 本轮结论

整站已经从“局部样式优化”进入“可扩展设计 Token 体系”阶段。后续新增文章、分类、案例和服务页面，应优先复用本轮建立的通用类，避免重新散落自由样式。

## 11. 下一轮建议

1. 用浏览器截图检查首页、文章页、服务页、诊断页的移动端信息密度。
2. 如继续扩展内容，可优先把 FAQ 聚合页和分类页做成统一列表模板。
3. 上线前确认正式域名后，再统一替换 canonical 常量。
