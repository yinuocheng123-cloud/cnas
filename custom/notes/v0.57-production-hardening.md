# 版本记录：v0.57-production-hardening

## 1. 本轮目标

本轮目标是对站点做上线前生产化收口，重点处理正式域名、线索闭环、安全审计、日志脱敏、SEO 基础和部署文件边界。目标不是视觉改版，也不是新增复杂后台或数据库。

## 2. 背景与上下文

本轮承接 `v0.56-production-launch-audit`。上一轮结论是：页面、构建和核心路由已经具备上线试运行基础，但仍有正式域名环境变量、依赖安全、线索存储、日志和部署源清理等上线前风险。

## 3. 问题分析

上线前的核心矛盾不是内容是否足够，而是生产环境是否可控：

1. 未配置 `SITE_URL` 时，sitemap、robots、canonical 和 Open Graph 会回退到 localhost。
2. 线索提交只有单一联系方式字段，无法清晰区分电话、微信、企业名称、来源页面和 UTM。
3. 生产日志会打印完整线索记录，存在隐私暴露风险。
4. robots 未屏蔽 `/admin`、`/api` 和 `/data`。
5. 本地日志、截图、cloudflared 工具和真实线索数据不应进入部署源。

## 4. 候选方案比较

方案一：上线前接入数据库和完整后台。

- 优点：线索持久化更长期。
- 缺点：上线前引入数据库、鉴权和迁移风险，超出本轮收口目标。
- 结论：放弃，留到上线后迭代。

方案二：保留本地 JSON 兜底，强化 webhook、字段校验、日志脱敏和部署边界。

- 优点：改动小，能明显降低明天上线风险。
- 缺点：serverless 环境中 JSON 仍不适合作为长期主存储。
- 结论：采用。

方案三：执行 `npm audit fix --force`。

- 优点：可能消除 audit 残余项。
- 缺点：npm 提示会安装破坏性版本，存在框架大幅回退风险。
- 结论：不采用。

## 5. 最终决策

采用最小生产化收口方案：

- 继续用 `SITE_URL` 统一站点地址，并在生产缺失时输出 warning。
- 线索字段补齐称呼、企业名称、电话、微信、需求描述、来源页面和 UTM。
- 生产日志只打印脱敏字段。
- webhook 配置缺失或失败时明确记录。
- robots 屏蔽非公开路径。
- `.gitignore` 排除本地运行产物和真实线索文件。

## 6. 具体实现

修改文件：

- `lib/seo.ts`：生产环境缺少 `SITE_URL` 时输出 warning。
- `app/layout.tsx`：增加基于 `SITE_URL` 的 WebSite JSON-LD。
- `app/robots.ts`：增加 `/admin`、`/api`、`/data` disallow。
- `components/LeadCaptureForm.tsx`：补齐称呼、企业、电话、微信、需求、来源和 UTM 提交，增加隐私提示和重复点击防护。
- `app/api/lead/route.ts`：增加字段长度限制、异常内容清洗、电话/微信校验、短时间重复提交防护、生产日志脱敏和 webhook 状态处理。
- `lib/lead-storage.ts`：扩展线索数据类型，增加短时间重复线索判断。
- `lib/webhook.ts`：扩展 webhook 消息字段，增加统一通知结果。
- `app/admin/leads/page.tsx`：后台列表显示称呼和企业名称。
- `.gitignore`：排除本地日志、截图、cloudflared 工具和 `data/leads.json`。
- `README.md`：补充 v0.57 上线环境变量和部署注意事项。
- `package-lock.json`：执行 `npm audit fix --omit=dev` 后更新 Next.js 实际解析版本。

## 7. 本轮优点

- 生产环境不会再打印完整电话、微信、企业需求等敏感线索。
- 线索字段更适合真实顾问跟进。
- webhook 未配置或失败时有明确日志，不再静默。
- sitemap、robots、canonical、Open Graph 和 JSON-LD 都继续通过 `SITE_URL` 控制。
- robots 不再鼓励抓取后台、接口和数据路径。
- 部署源边界更清晰，减少误提交本地运行产物的风险。

## 8. 本轮缺点与代价

- 仍未接入真实数据库，本地 JSON 只能作为兜底。
- 短时间重复提交防护是轻量文件级判断，不适合高并发。
- `npm audit --omit=dev` 仍有 moderate 残余项；不执行 `--force` 是为了避免破坏性 Next.js 版本变更。
- 表单字段增加后，诊断页移动端会比之前稍长，但这是为了真实线索质量接受的代价。

## 9. 验证与结果

本轮已执行：

初始结果：

- `build` 通过。

修复后结果：

- `typecheck` 通过。
- `build` 通过。

- `npm audit --omit=dev` 仍有 2 个 moderate 残余项，npm 建议的修复需要 `--force`，本轮未执行。

## 10. 本轮结论

当前版本比 `v0.56` 更接近可上线试运行状态。明天上线前必须配置真实 `SITE_URL`、`ADMIN_KEY` 和至少一个线索 webhook。若部署到 Vercel 等 serverless 平台，不应依赖 `data/leads.json` 作为正式主存储。

## 11. 下一轮建议

1. 上线后第一天重点观察表单提交成功率、webhook 到达率、404、500 和页面访问路径。
2. 若开始投流或收集真实线索，优先把线索存储迁移到数据库或稳定外部表单服务。
3. 在 Next.js 官方安全修复更稳定后，继续跟进 `npm audit` 残余项，不建议用 `--force` 回退框架大版本。
