# CNAS内容控制台轻量 CMS 后台规划

## 1. 后台定位

CNAS内容控制台是 `www.cnaszhinan.com` 主站的轻量内容运营后台，只服务于网站内容管理和上线后基础运营，不承担 CRM、客户跟进、销售流程、企业微信增长中台或复杂业务系统职责。

后台建议路径为 `/admin`，继续使用现有 `ADMIN_KEY` 做简单访问保护。第一版只面向内部少量运营人员使用，不做多角色权限、不做账号体系、不接复杂数据库、不接企业微信 API、不做 AI 自动写文章。

后台的核心原则：

- 只管理网站内容和基础运营信息。
- 优先复用现有文章、FAQ、栏目、线索和站点配置。
- 第一版先做轻量、可控、可回退，不追求完整 CMS 平台。
- 避免后台编辑直接造成线上内容不可追踪，内容发布仍建议保留 Git 提交记录。

## 2. 模块结构

后台只包含 5 个模块：

1. 文章管理
2. FAQ 管理
3. 栏目管理
4. 线索查看
5. 站点设置

建议 `/admin` 首页作为控制台总览，展示：

- 内容总数：文章数、FAQ 数、栏目数。
- 最近线索：只读展示最近若干条。
- 站点状态：`SITE_URL`、webhook 是否配置、备案号是否配置。
- 快捷入口：文章管理、FAQ 管理、栏目管理、线索查看、站点设置。

## 3. 每个模块字段

### 3.1 文章管理

定位：管理 `/articles` GEO 文章和后续行业内容，不做 AI 自动写作。

第一版字段建议：

- `id`：内部唯一标识。
- `slug`：URL 路径片段。
- `title`：文章标题。
- `description`：SEO 描述和列表摘要。
- `category`：文章分类。
- `mainKeyword`：主关键词。
- `relatedKeywords`：相关关键词数组。
- `publishDate`：发布日期。
- `status`：`draft` / `published` / `archived`。
- `conclusion`：一句话结论。
- `definition`：标准定义段。
- `sections`：正文段落结构。
- `table`：表格数据。
- `faqs`：文章内 FAQ。
- `nextSteps`：下一步建议。
- `updatedAt`：最后更新时间。

第一版页面能力：

- 文章列表：标题、分类、状态、发布日期、更新时间。
- 文章详情预览：按前台文章页结构只读预览。
- 草稿编辑建议：第一版可先规划，不强制上线可写编辑器。
- 发布提醒：提示内容发布应经过 Git 提交与构建部署。

### 3.2 FAQ 管理

定位：管理全站常见问题，包括 `/faq`、`/faqs` 和文章内 FAQ 的基础入口。

第一版字段建议：

- `id`：内部唯一标识。
- `question`：问题。
- `answer`：回答。
- `category`：所属分类，例如路径判断、认可准备、评审整改、认可后维护、常见问题。
- `source`：来源位置，例如平台 FAQ、文章 FAQ、知识库 FAQ。
- `relatedUrl`：关联页面路径。
- `status`：`draft` / `published` / `archived`。
- `sortOrder`：排序。
- `updatedAt`：最后更新时间。

第一版页面能力：

- FAQ 列表：按分类筛选。
- FAQ 详情：查看问题、回答、关联页面。
- 重复问题提醒：手动标记相似问题，避免内容重复。

### 3.3 栏目管理

定位：管理主站平台栏目和内容分类，不做复杂频道系统。

第一版字段建议：

- `id`：内部唯一标识。
- `slug`：栏目路径片段。
- `title`：栏目名称。
- `description`：栏目说明。
- `path`：真实页面路径。
- `type`：平台页、知识库分类、GEO 文章分类、服务栏目。
- `status`：`enabled` / `disabled`。
- `sortOrder`：排序。
- `seoTitle`：SEO 标题。
- `seoDescription`：SEO 描述。
- `updatedAt`：最后更新时间。

第一版页面能力：

- 栏目列表：展示路径、类型、状态。
- 栏目详情：只读查看当前栏目配置。
- 导航关联检查：提示首页、Header、Footer 是否已有入口。

### 3.4 线索查看

定位：沿用现有 `/admin/leads` 的线索只读查看能力，不扩展为 CRM。

第一版字段建议继续复用现有线索结构：

- `id`：线索 ID。
- `createdAt`：提交时间。
- `name`：称呼或联系人。
- `company`：企业名称。
- `enterpriseType`：企业或实验室类型。
- `stage`：当前阶段。
- `phone`：电话。
- `wechat`：微信。
- `contact`：联系方式汇总。
- `sourcePage`：来源页面。
- `utmSource`：UTM source。
- `utmMedium`：UTM medium。
- `utmCampaign`：UTM campaign。
- `deliveryStatus`：通知状态。

第一版页面能力：

- 线索列表：只读展示。
- 基础筛选：按日期、来源页、当前阶段筛选。
- 线索详情：展示完整 payload。
- 导出建议：第一版可先保留规划，不立即开发导出。

明确不做：

- 客户跟进状态。
- 顾问分配。
- 跟进记录。
- 客户标签自动化。
- CRM 看板。

### 3.5 站点设置

定位：展示网站基础配置状态，不在后台明文展示密钥。

第一版字段建议：

- `siteUrlConfigured`：`SITE_URL` 是否配置。
- `adminKeyConfigured`：`ADMIN_KEY` 是否配置。
- `feishuWebhookConfigured`：`LEAD_WEBHOOK_FEISHU` 是否配置。
- `wechatWebhookConfigured`：`LEAD_WEBHOOK_WECHAT` 是否配置。
- `gaIdConfigured`：`NEXT_PUBLIC_GA_ID` 是否配置。
- `icpText`：备案号文本。
- `icpUrl`：备案链接。
- `wecomQrPath`：企业微信二维码公开路径。
- `updatedAt`：配置检查时间。

第一版页面能力：

- 只显示“已配置 / 未配置 / 为空”，不显示真实密钥。
- 显示备案号和二维码路径。
- 显示站点健康提醒，例如 webhook 未配置时提示“线索不会主动通知运营人员”。

## 4. 页面路由建议

建议保留现有 `/admin/leads`，并新增统一后台入口：

- `/admin`：后台总览。
- `/admin/articles`：文章管理列表。
- `/admin/articles/[slug]`：文章详情预览。
- `/admin/faqs`：FAQ 管理列表。
- `/admin/faqs/[id]`：FAQ 详情。
- `/admin/categories`：栏目管理。
- `/admin/leads`：线索查看，沿用现有页面。
- `/admin/leads/[id]`：线索详情，后续可选。
- `/admin/settings`：站点设置。

访问保护建议：

- 第一版沿用 query key：`/admin?key=ADMIN_KEY`。
- 后台内部链接保留 `key` 参数，避免跳转后丢失访问权限。
- 不在页面中显示 `ADMIN_KEY` 原文。
- 若后续需要更安全体验，再升级为 httpOnly cookie 登录态。

## 5. 数据结构建议

当前项目已有数据基础：

- GEO 文章：`lib/geo-articles.ts`
- 平台基础页：`lib/platform-pages.ts`
- 知识库、导航、方案、案例、FAQ 等：`lib/site-data.ts`
- 线索数据：`data/leads.json`，通过 `lib/lead-storage` 读取
- 站点 SEO 和 SITE_URL：`lib/seo.ts`

第一版不建议后台直接写 TypeScript 源文件，因为线上服务器写入 Git 跟踪文件容易造成部署漂移。建议分两层设计：

### 5.1 第一阶段：只读控制台 + 草稿记录

数据来源仍读取现有 TS 数据和本地线索文件。

后台可先提供：

- 内容只读列表。
- 内容详情预览。
- 配置状态检查。
- 草稿规划字段，但不直接发布。

如必须保存草稿，可考虑新增未跟踪或受控的草稿文件：

- `data/cms-drafts/articles.json`
- `data/cms-drafts/faqs.json`

但第一版上线前应先确认是否需要让草稿进入 Git。若要长期维护内容，建议草稿也通过 Git 提交进入仓库，而不是只留服务器。

### 5.2 第二阶段：内容数据 JSON 化

在不接数据库的前提下，可逐步将可运营内容迁移为本地 JSON 或 Markdown：

- `content/articles/*.md`
- `content/faqs.json`
- `content/categories.json`

前台通过统一 content adapter 读取，后台写入草稿或正式内容文件。

优点：

- 不接数据库。
- 内容可通过 Git 追踪。
- 容易回滚。
- 适合小型内容站。

代价：

- 多人同时编辑能力弱。
- 后台写文件需要谨慎处理并发和权限。
- 发布仍需要构建部署流程。

## 6. 第一版开发范围

推荐第一版只做“轻量可用控制台”，开发范围如下：

1. `/admin` 总览页。
2. 统一 `ADMIN_KEY` 访问保护封装。
3. 文章管理只读列表和详情预览。
4. FAQ 管理只读列表和详情预览。
5. 栏目管理只读列表。
6. 线索查看继续复用现有 `/admin/leads`，可补详情页但不做跟进系统。
7. 站点设置只显示配置状态，不显示真实值。
8. 后台内部链接保留 key 参数。
9. 后台页面移动端可用，但优先桌面运营体验。

第一版不建议立即做在线发布。更稳的方式是：

- 后台先帮运营人员看清内容体系。
- 内容新增和修改仍通过本地代码提交。
- 等内容结构稳定后，再做文件型编辑和发布。

## 7. 暂不开发范围

第一版明确不做：

- 多账号、多角色、权限矩阵。
- 数据库和 ORM。
- 复杂富文本编辑器。
- AI 自动写文章。
- 企业微信 API。
- 飞书表格同步。
- 客户跟进系统。
- CRM 看板。
- 自动分配顾问。
- 自动标签。
- 自动生成报告。
- 内容审核流。
- 图片素材库。
- 定时发布。
- 站内搜索后台。
- 支付、订单、合同、工单。

这些能力如果提前引入，会把“内容控制台”变成业务系统，增加维护成本和上线风险。

## 8. 后续升级方向

后续可以按运营成熟度逐步升级：

### 8.1 内容编辑升级

- 将文章从 TS 数据迁移为 Markdown 或 JSON。
- 增加草稿、预览、发布状态。
- 增加基础 Markdown 编辑器。
- 增加 SEO 字段校验。

### 8.2 安全升级

- 从 query key 升级为一次登录后写入 httpOnly cookie。
- 增加后台访问日志。
- 增加失败访问限流。
- 将 ADMIN_KEY 定期轮换流程写入运维文档。

### 8.3 内容质量升级

- 增加风险词扫描。
- 增加“CNAS认证”误用提醒。
- 增加站内链接检查。
- 增加 sitemap 覆盖检查。

### 8.4 数据持久化升级

如未来内容量明显增加，再考虑数据库：

- SQLite：适合单机轻量后台。
- PostgreSQL：适合多人运营和后续业务系统。

但当前阶段不建议直接接数据库。

## 9. 风险提醒

1. **ADMIN_KEY 只是轻量保护，不是完整账号体系。**
   第一版适合小范围内部使用，不适合多人长期运营。

2. **后台直接写源码文件风险较高。**
   如果服务器直接改 Git 跟踪文件，后续 `git pull --ff-only` 可能出现冲突。因此第一版建议只读和草稿优先。

3. **不接数据库会限制多人协作。**
   文件型 CMS 适合轻量运营，但不适合多人同时编辑。

4. **内容发布仍需要构建部署。**
   当前 Next.js 内容大多是静态生成，文章更新后需要重新 build 和重启服务。

5. **线索查看不能扩展成 CRM。**
   如果在该后台里继续加入跟进状态、客户标签、分配顾问，就会偏离本轮定位。

6. **密钥不能在后台明文展示。**
   站点设置只展示配置状态，不显示 ADMIN_KEY、webhook、服务器密码等真实值。

## 10. 推荐实施顺序

建议分 4 步实施：

1. **建立后台壳子**
   新增 `/admin` 总览页和统一访问保护，整合现有 `/admin/leads` 入口。

2. **接入只读内容管理**
   先做文章、FAQ、栏目列表与详情预览，全部读取现有数据，不写入。

3. **补站点设置和健康检查**
   展示环境变量配置状态、备案号、二维码路径、webhook 是否可用。

4. **再评估是否需要可写草稿**
   如果运营确实需要后台录入内容，再引入 `content/` 或 `data/cms-drafts/` 的文件型草稿机制，并设计 Git 提交与发布流程。

当前最推荐的第一版范围是：`后台壳子 + 只读内容管理 + 线索查看 + 站点设置状态`。这样能最快形成内容控制台，同时不破坏当前已上线的主站结构。
