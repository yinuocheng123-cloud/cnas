# 版本记录：v0.1-nextjs-app-router-baseline

## 1. 本轮目标

本轮目标是为空仓库建立首个可迭代的技术基线，覆盖 Next.js App Router、TypeScript、Tailwind CSS，并在 Demo 阶段使用本地 TypeScript 数据文件模拟内容。

目标类型：功能补充、可维护性提升。

## 2. 背景与上下文

本轮开始前仓库只有 `.git` 目录，没有可读取的 `AGENTS.md` 文件、历史记录、业务代码或配置文件。用户在对话中提供了代理规则，并明确技术栈方向：Next.js App Router、TypeScript、Tailwind CSS、Prisma 预留、PostgreSQL 预留、本地 TypeScript 数据模拟内容。

Git 同步方面，已尝试执行 `git pull --ff-only`，但当前分支没有上游跟踪信息，且 `git remote -v` 为空，因此无法从 GitHub 拉取最新内容。

## 3. 问题分析

当前核心问题不是修复既有功能，而是在空仓库中建立后续迭代的最小基线。若直接引入数据库、后台管理或复杂数据层，会在需求尚未明确时提前锁定结构，增加后续返工成本。

本轮主要矛盾是：既要满足指定技术栈，又要避免 Demo 阶段过早引入真实数据库复杂度。

## 4. 候选方案比较

方案一：完整接入 Prisma 与 PostgreSQL。

优点是后续数据库路径更接近真实生产形态。缺点是需要 `.env`、数据库实例、迁移策略和生成客户端，当前需求只要求预留，成本和风险偏高，因此本轮放弃。

方案二：只建立 Next.js + TypeScript + Tailwind 页面，完全不放 Prisma 文件。

优点是最小可运行。缺点是没有体现 Prisma/PostgreSQL 的预留方向，后续代理需要重新判断数据库入口，因此本轮未选择。

方案三：页面使用本地 TypeScript 数据，仓库保留 Prisma schema 草案但不接入运行路径。

优点是 Demo 可直接运行，数据字段有类型约束，同时为未来数据库替换留出明确位置。缺点是 Prisma schema 尚未经过真实业务验证，后续可能需要调整字段。最终选择该方案。

## 5. 最终决策

最终采用 Next.js App Router 首页直接读取 `lib/demo-data.ts` 的方式，先让内容展示闭环成立。Prisma/PostgreSQL 仅通过 `prisma/schema.prisma` 预留，不在页面层导入 Prisma Client，也不生成迁移。

这样设计的原因是：Demo 阶段的主要价值是确认信息结构和页面消费方式，而不是证明数据库接入能力。

## 6. 具体实现

新增 `package.json`，定义 Next.js、React、TypeScript、Tailwind、Prisma 相关依赖与脚本。

新增 `app/layout.tsx`、`app/page.tsx`、`app/globals.css`，建立 App Router 页面、全局样式和 Tailwind 入口。

新增 `lib/demo-data.ts`，用 TypeScript 类型和本地数组模拟内容数据。

新增 `prisma/schema.prisma`，保留 PostgreSQL 数据源和 `ContentItem` 草案模型。

新增 `tailwind.config.ts`、`postcss.config.mjs`、`next.config.mjs`、`tsconfig.json`、`.gitignore`、`README.md`，补齐项目基础配置。

## 7. 本轮优点

当前方案结构简单，页面层数据来源明确，后续从本地数据切换到数据库查询时可以优先替换数据读取层。

Prisma 没有进入运行路径，因此不会因为缺少数据库或 Prisma Client 生成结果阻塞 Demo 页面。

Tailwind 配置和页面样式已经形成可视化基线，后续可以在同一约定下继续扩展。

## 8. 本轮缺点与代价

当前没有真实数据库连接，也没有 Prisma Client 生成和迁移验证，因此数据库部分只是方向预留，不代表最终模型已经确认。

`ContentItem` 模型是根据 Demo 内容字段推导出的草案，未来若业务需要作者、状态、封面、排序或多语言字段，可能要推翻或扩展。

本轮没有引入测试框架，验证主要依赖类型检查、构建或开发服务器启动。

## 9. 验证与结果

本轮计划执行依赖安装后的 `npm run typecheck` 或 `npm run build` 作为最小验证。

若依赖安装因网络或环境限制失败，需要在最终回复中说明未完成的验证项。

## 10. 本轮结论

首轮基线应优先保持轻量：本地 TypeScript 数据足以支撑 Demo 内容流，Prisma/PostgreSQL 只需要清楚预留，不应提前进入页面运行路径。

后续默认继承的经验是：页面组件消费稳定的数据形状，数据来源可以延后替换。

## 11. 下一轮建议

第一，确认 Demo 内容真实业务类型，再调整 `DemoItem` 与 `ContentItem` 字段。

第二，确认是否需要真实 PostgreSQL 环境，再补充 `.env.example`、Prisma Client 生成和迁移策略。

第三，若页面继续扩展，建议先拆分可复用 UI 组件，但不要在单页阶段过早抽象。
