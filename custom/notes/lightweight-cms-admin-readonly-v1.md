# 版本记录：lightweight-cms-admin-readonly-v1

## 1. 本轮目标

本轮目标是基于 `custom/notes/lightweight-cms-admin-plan.md`，开发第一版“CNAS内容控制台”后台壳子与只读管理能力。

本轮属于功能补充，但严格限定为只读后台：

- 新增 `/admin` 后台首页；
- 新增文章、FAQ、栏目、站点设置只读页；
- 保留现有 `/admin/leads` 线索查看能力；
- 复用现有 `ADMIN_KEY` 简单访问保护；
- 不做新增、编辑、删除；
- 不接数据库；
- 不做 CRM；
- 不做企业微信 API；
- 不让服务器后台直接写 Git 跟踪源码文件。

用户补充提到“后台编辑器，可以自动适用 Word 文本格式”。该能力涉及富文本解析、草稿发布、源码写入或内容存储方案，和本轮“只读后台”边界冲突，因此本轮不实现，只作为后续升级方向记录。

## 2. 背景与上下文

本轮承接 `lightweight-cms-admin-plan.md`。规划文档已明确后台定位为“CNAS内容控制台”，只服务于网站内容运营，不是业务系统，也不是客户管理系统。

修改前状态：

- 项目已有 `/admin/leads`，通过 `ADMIN_KEY` query 参数保护；
- 文章数据来自 `lib/geo-articles.ts`；
- 平台栏目数据来自 `lib/platform-pages.ts`；
- FAQ 数据部分来自 `src/data/faqs.ts`，部分分散在平台页和文章数据中；
- 线索读取能力来自 `lib/lead-storage.ts`；
- 站点已有主站前台、文章页、栏目页、线索 API、webhook 逻辑。

本轮必须避免影响：

- `/articles` 和 20 篇 GEO 文章详情；
- `/path`、`/prepare`、`/review`、`/maintenance`、`/faq`；
- `/api/lead`；
- `/admin/leads` 原有查看方式；
- SEO、sitemap、robots、canonical、OG；
- 生产环境变量和密钥文件。

## 3. 问题分析

当前网站已经具备内容体系，但运营入口分散：

- 文章列表只能从前台查看，不方便快速核对主词、分类、发布时间；
- FAQ 分散在问答库、平台页和文章页中，不方便整体检查；
- 栏目内容虽已落地，但缺少只读总览；
- 站点环境变量配置状态只能通过服务器文件确认，不适合日常运营人员判断；
- 线索页已有，但没有被放进统一后台导航。

核心矛盾是：需要一个运营视角的后台入口，但第一版不能引入写入风险。尤其文章和 FAQ 目前仍是 Git 跟踪源码数据，如果直接做在线编辑，会带来发布流程、冲突处理、权限和审计问题。

## 4. 候选方案比较

### 方案一：直接开发可编辑 CMS

核心思路：后台提供文章和 FAQ 新增、编辑、删除，直接修改本地数据文件。

优点：

- 运营体验最直接；
- 后台看起来更像完整 CMS。

缺点：

- 会让服务器后台直接写 Git 跟踪源码文件；
- 容易和 GitHub 部署流程产生冲突；
- 需要草稿、发布、回滚、权限和格式清洗；
- Word 文本格式适配还需要富文本解析和安全过滤。

放弃原因：超出本轮明确边界，也不符合“不做复杂系统、不接数据库、不写源码文件”的要求。

### 方案二：只做 `/admin/leads` 小修

核心思路：保留原线索页，仅增加一个简单返回链接。

优点：

- 改动最小；
- 风险最低。

缺点：

- 无法满足文章、FAQ、栏目、设置 5 个后台模块的规划；
- 无法形成“内容控制台”壳子。

放弃原因：无法覆盖本轮要求。

### 方案三：只读后台壳子 + 数据聚合视图

核心思路：复用现有本地数据结构，新增后台首页和只读管理页，只展示数据状态，不写入任何业务数据。

优点：

- 满足第一版后台规划；
- 不引入数据库；
- 不破坏 Git 发布流程；
- 对前台、接口、webhook 影响小；
- 为后续编辑器、Word 文本导入和草稿发布预留方向。

缺点：

- 暂时不能在线编辑；
- FAQ 聚合只能按现有数据来源展示，无法替代真正的内容模型；
- 设置页只能显示配置状态，不显示也不修改真实值。

最终选择：方案三。

## 5. 最终决策

本轮采用“只读后台壳子 + 数据聚合视图”。

关键设计决策：

- 抽出 `lib/admin.ts`，集中处理 ADMIN_KEY 校验、后台链接、FAQ 聚合、栏目聚合和设置状态；
- 新增 `components/admin/AdminShell.tsx`，统一后台导航与页面壳子；
- `/admin` 展示 5 个入口卡片和基础统计；
- `/admin/articles` 读取 `geoArticles`，支持分类筛选和标题搜索；
- `/admin/faqs` 聚合平台页 FAQ、GEO 文章 FAQ 和问答库 FAQ；
- `/admin/categories` 展示平台基础栏目；
- `/admin/settings` 只显示环境变量是否配置，不暴露密钥；
- `/admin/leads` 继续读取现有线索数据，并接入统一后台导航。

## 6. 具体实现

涉及文件：

- `lib/admin.ts`
  - 新增 ADMIN_KEY 访问保护；
  - 新增后台链接构造；
  - 新增 FAQ 聚合；
  - 新增栏目聚合；
  - 新增站点配置状态聚合。

- `components/admin/AdminShell.tsx`
  - 新增统一后台壳子；
  - 提供后台导航：首页、文章、FAQ、栏目、线索、设置、返回前台。

- `app/admin/page.tsx`
  - 新增后台首页；
  - 展示文章数、FAQ 数、栏目数、线索数、最近更新时间；
  - 展示五个入口卡片。

- `app/admin/articles/page.tsx`
  - 新增文章管理只读页；
  - 展示标题、分类、主词、发布时间、状态、前台链接；
  - 支持分类筛选和标题搜索。

- `app/admin/faqs/page.tsx`
  - 新增 FAQ 管理只读页；
  - 展示问题、分类、是否首页展示、来源页面；
  - 支持分类筛选。

- `app/admin/categories/page.tsx`
  - 新增栏目管理只读页；
  - 展示栏目名称、路径、说明、推荐文章数量、前台链接。

- `app/admin/settings/page.tsx`
  - 新增站点设置只读页；
  - 显示 `SITE_URL`、`ADMIN_KEY`、`LEAD_WEBHOOK_FEISHU`、`LEAD_WEBHOOK_WECHAT`、`NEXT_PUBLIC_GA_ID` 是否配置；
  - 显示网站名称、平台定位、联系方式占位状态、企业微信二维码状态。

- `app/admin/leads/page.tsx`
  - 保留线索只读查看能力；
  - 接入统一后台壳子；
  - 不修改线索 API 和数据写入逻辑。

## 7. 本轮优点

- 形成了 CNAS内容控制台的第一版后台入口；
- 复用了现有数据结构，没有新增数据库；
- 统一了后台导航，后续扩展页面更清晰；
- 后台全部只读，避免破坏 Git 跟踪源码；
- 设置页只显示配置状态，不暴露敏感值；
- 线索页继续沿用原有读取逻辑，降低回归风险；
- 为后续“编辑器”和“Word 文本格式适配”留下了边界清晰的升级方向。

## 8. 本轮缺点与代价

- 第一版不能编辑文章、FAQ 或栏目；
- FAQ 聚合仍依赖现有分散数据源，没有形成统一内容模型；
- “是否首页展示”只能基于当前已知首页问题做轻量判断，不能替代真正的发布状态字段；
- 设置页不能直接修改配置，只能辅助检查；
- 后续如果要支持 Word 文本格式，需要新增草稿层、格式清洗、发布审核和 Git 同步策略，本轮未处理。

## 10. 本轮结论

本轮把“轻量 CMS 后台”从规划推进到第一版只读可用状态。当前最重要的结论是：在内容仍由 Git 跟踪源码承载时，后台第一版应先做只读总览，不应直接做在线编辑。

这个边界可以保护当前上线稳定性，也为后续内容模型升级留出空间。

## 11. 下一轮建议

1. 先让运营人员使用只读后台核对文章、FAQ、栏目和线索，确认字段是否够用。
2. 如果要做编辑器，优先设计“草稿导入 + 人工发布”流程，不要直接在线写源码。
3. Word 文本格式适配建议作为独立二期：先支持粘贴后的标题、段落、列表、表格清洗，再考虑文章发布。
