# 版本记录：v0.14-content-guide

## 1. 本轮目标

本轮目标是补充一份面向后续内容维护的 `CONTENT_GUIDE.md`，说明当前项目在哪里新增文章、栏目、标签、FAQ、案例、服务和首页导航内容，并为每一类提供最小新增示例。

本轮目标属于文档补充和可维护性提升，不修改业务页面结构，不调整数据模型，不新增运行功能。

## 2. 背景与上下文

本轮承接 `custom/notes/v0.13-design-token-system.md`。上一轮已经完成设计 Token 与组件样式收口，当前项目进入“内容持续扩展”阶段。后续如果没有清晰的内容维护入口，新增文章和栏目时容易误改页面组件，或忘记同步标签、FAQ、sitemap 与验证命令。

## 3. 问题分析

项目内容分散在 `src/data/articles.ts`、`src/data/categories.ts`、`src/data/tags.ts`、`src/data/cases.ts`、`src/data/services.ts` 和 `lib/site-data.ts`。这些文件职责不同，但都影响前台展示和 SEO 收录。

核心问题不是缺功能，而是缺少一份可交接的内容操作说明。

## 4. 候选方案比较

方案一：只在 README 中补充一段内容维护说明。

优点是入口集中，缺点是 README 已承担项目概览职责，继续塞入大量示例会降低可读性，因此放弃。

方案二：新增独立 `CONTENT_GUIDE.md`。

优点是内容维护者可以直接查阅，示例可以写得更具体，也不会干扰 README。最终选择该方案。

## 5. 最终决策

新增根目录 `CONTENT_GUIDE.md`，按内容类型拆分说明：

- 文章
- 栏目
- 标签
- FAQ
- 案例
- 服务
- 首页导航与首页入口
- sitemap 与 SEO
- 新增内容后的验证命令

## 6. 具体实现

新增 `CONTENT_GUIDE.md`，为每类内容写明维护文件、影响路由、注意事项和新增示例。重点说明 FAQ 会从文章中自动聚合，标签只有被文章使用后才有有效聚合页，sitemap 会自动读取文章、栏目、标签和方案数据。

## 7. 本轮优点

后续新增内容时，不需要重新阅读全部代码即可知道应该改哪个数据文件。文档也明确要求新增后执行 `npm run typecheck` 和 `npm run build`，降低内容变更造成构建失败的风险。

## 8. 本轮缺点与代价

本轮没有把内容新增流程做成脚手架命令，仍需要人工编辑 TypeScript 数据文件。对于大量内容导入，未来可能需要进一步引入内容生成脚本或 CMS，但 Demo 阶段保持手动维护更可控。

## 9. 验证与结果

本轮需要执行 `npm run typecheck` 和 `npm run build`，确认新增 Markdown 文档不影响项目类型检查和生产构建。

## 10. 本轮结论

`CONTENT_GUIDE.md` 可以作为后续内容扩展的操作入口，明确了内容数据、首页入口、聚合页、sitemap 与验证流程之间的关系。

## 11. 下一轮建议

1. 如果后续文章数量增加，可以新增内容模板文件，减少手写字段遗漏。
2. 如果栏目继续扩展，可以抽象顶层栏目页生成方式，减少新增 `app/<slug>/page.tsx` 的重复。
3. 上线前继续保持新增内容后执行 typecheck 与 build 的习惯。
