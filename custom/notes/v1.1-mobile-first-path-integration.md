# 版本记录：v1.1-mobile-first-path-integration

## 1. 本轮目标

本轮目标是只改造 CNAS认可指南主站，把原 path.cnaszhinan.com 成交页中已经验证过的核心成交逻辑整合进 cnaszhinan.com 首页。

本轮属于上线后的主站转化整合，不新增后台、不新增数据库、不重构客户管理系统，重点是让主站首页同时承担内容信任、路径判断、企业微信承接、基础信息提交、A/B/C 初步诊断和后续维护入口。

## 2. 背景与上下文

本轮承接以下历史记录：

- `custom/notes/post-launch-operation-check.md`
- `custom/notes/server-lead-endpoint-integration-2026-05-25.md`
- `custom/notes/v0.59-production-final-cleanup.md`

上一轮已经确认主站 `/api/lead` 可以接收成交页线索字段，后台可通过 `ADMIN_KEY` 查看线索，成交页表单已经真实进入主站后台。用户本轮明确要求不再继续优化 `path.cnaszhinan.com`，而是把成交逻辑整合到主站，并让旧成交页后续不再作为独立成交系统使用。

## 3. 问题分析

整合前的核心矛盾是：主站更像内容入口，成交页承担了主要转化逻辑，两套入口会造成运营分散、后续维护重复，也容易在重新部署时出现主站与成交页状态不一致。

本轮不能简单复制成交页整页，因为成交页是独立静态落地页，结构、视觉和脚本都与主站 Next.js 架构不同。更合适的方式是提取已经验证过的核心转化逻辑：路径判断问卷、企业微信承接、A/B/C 初步诊断、线索 payload 字段和认可后维护表达，然后重构成主站首页的一部分。

## 4. 候选方案比较

方案一：保留主站首页，只增加一个跳转到成交页的入口。

优点是改动最小，风险低。缺点是无法满足用户“path 不再作为独立成交系统使用”的目标，也没有解决两套入口分散的问题。本轮放弃。

方案二：把成交页整页复制到主站首页。

优点是可以快速复用已有页面。缺点是会破坏主站整体调性，造成重复代码和重复表单，也可能丢失原主站 SEO 与导航结构。本轮放弃。

方案三：在主站首页重构一个 mobile-first 路径判断体验，只提取成交页核心逻辑。

优点是保留主站品牌和后台体系，同时把转化链路前置到首页，手机端更清楚，后续只维护主站一套入口。缺点是首页改动较大，需要重新验证构建、表单、二维码、备案号和旧成交页跳转。本轮采用该方案。

## 5. 最终决策

最终采用“主站首页 mobile-first 路径判断整合”方案。

关键决策：

- 首页首屏围绕“做CNAS认可，先判断路径，再决定怎么启动”展开。
- 路径判断模块使用锚点 `#path-check`，便于旧成交页 301 到主站对应位置。
- 表单继续提交到主站现有 `/api/lead`，不新增接口、不改后台权限。
- A/B/C 初步诊断在前端即时生成，提交时把诊断摘要写入 payload。
- 企业微信二维码复制到主站 `public/wecom-qr.png`，不直接引用成交页目录。
- Footer 改成品牌信任、服务内容、企业微信承接和备案号结构。

## 6. 具体实现

涉及文件：

- `app/page.tsx`：首页改为渲染 `MobileFirstPathHome`，保留 Header、Footer 与 metadata。
- `components/MobileFirstPathHome.tsx`：新增主站首页路径判断体验，包含首屏、痛点、六项判断、问卷、A/B/C 诊断、企业微信承接、认可后维护和 FAQ。
- `components/MobileFirstPathHome.tsx`：保留知识库、行业方案和案例的轻量内链入口，避免主站首页从资讯入口调整为转化入口后丢失重要 SEO 路径。
- `components/Footer.tsx`：重做为三栏 footer，保留准确备案号 `浙ICP备2020044218号-3` 和工信部备案链接。
- `public/wecom-qr.png`：从旧成交页复制真实企业微信二维码到主站公开资源目录。
- `src/data/articles.ts`、`src/data/tags.ts`、`app/faqs/page.tsx`：将公开页面中的“CNAS认证”统一修正为“CNAS认可”，避免上线风险词。

## 7. 本轮优点

- 主站首页现在直接承接“内容信任 → 路径判断 → 初步诊断 → 线索提交 → 人工跟进”的最小运营闭环。
- 手机端首屏、问卷、按钮和二维码更靠前，减少用户在内容页和成交页之间跳转。
- 线索仍进入原有 `/api/lead` 和后台，不引入新系统，降低上线风险。
- 旧成交页后续可以通过 301 收口到主站路径判断区，减少维护面。
- 备案号和二维码进入主站仓库，后续重新部署不容易丢失线上补丁。

## 8. 本轮缺点与代价

本轮首页改动幅度较大，虽然没有改后台和接口，但首页信息结构已经从资讯型入口转为转化型入口，后续需要用户用手机实际查看首屏长度、按钮手感和二维码扫码体验。

A/B/C 诊断仍是轻量规则判断，不等同于正式咨询结论。为了避免过度乐观，冲突时优先按更高风险判断，但仍需要人工顾问后续确认。

当前 webhook 仍未配置时，线索只能进入本地备份和后台，不会主动通知运营人员。这不是本轮范围内修复的问题。

## 9. 验证与结果

本地已完成：

- `npm run typecheck`：通过。
- `npm run build`：通过。
- 公开代码风险词检查：`app`、`src`、`components`、`lib` 下未发现 `CNAS认证`、`包过`、`保证通过`、`官方指定`、`唯一`、`最权威`、`必过`、`100%通过`。

本地 build 中仍出现 `SITE_URL` 未配置警告，这是本地环境未加载生产 `.env.production` 的预期提醒；线上生产环境已配置 `SITE_URL=https://cnaszhinan.com`。

线上验证、PM2 重启、旧成交页 301 和后台测试线索会在服务器部署后继续记录到 `post-launch-operation-check.md`。

## 10. 本轮结论

主站已经具备承接原成交页核心转化逻辑的代码基础。后续上线后，`path.cnaszhinan.com` 不再需要作为独立成交系统继续运营，可以作为备份目录保留，并通过 Nginx 301 到 `https://cnaszhinan.com/#path-check`。

## 11. 下一轮建议

1. 部署后用真实手机检查首页首屏、问卷填写、诊断结果、二维码显示和 footer 备案号。
2. 配置至少一个 `LEAD_WEBHOOK_FEISHU` 或 `LEAD_WEBHOOK_WECHAT`，否则线索不会主动通知运营人员。
3. 观察 1 到 2 天主站表单提交情况，再决定是否进一步压缩首页内容或调整 CTA 文案。
