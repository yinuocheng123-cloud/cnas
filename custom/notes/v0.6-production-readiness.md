# 版本记录：v0.6-production-readiness

## 1. 本轮目标

本轮目标是按“可上线版本”标准完成上线前检查与收口，确保项目在未确认正式域名和远端推送前，已经具备本地部署验证基础。

目标类型：上线前自检、内容规范收口、构建验证、版本提交准备。

## 2. 背景与上下文

本轮承接 `custom/notes/v0.5-content-route-closure.md`。此前已完成 CNAS 专业内容平台结构、GEO/TEO/SEO 基础和路由扩展。

本轮开始执行 `git pull --ff-only`，远端已配置且返回 `Already up to date`。

## 3. 问题分析

上线前主要风险集中在四类：页面是否可访问、用词是否专业统一、SEO 与 sitemap 是否完整、移动端页面是否存在明显布局问题。

## 4. 候选方案比较

方案一：只执行构建验证。

优点是快速。缺点是无法覆盖内容用词、页面可访问性和移动端视觉风险，因此放弃。

方案二：按页面、内容、SEO、视觉、构建、启动逐项自检。

优点是覆盖上线前关键风险，且不涉及真实部署和远端推送。最终选择该方案。

## 5. 最终决策

保留当前技术栈和静态内容结构，不接入后台、会员、支付、复杂 CMS、真实数据库、多语言或复杂动画。

继续以 `https://www.hangyukeji.com` 作为 canonical 可配置常量，上线前需要人工确认真实域名。

## 6. 具体实现

更新 README 当前版本记录为 `v0.6 production readiness`。

继续保留全站用词规范：以“CNAS认可”为主，“CNAS认证”仅作为搜索兼容词。

执行全站低专业表达扫描、核心页面访问检查、移动端主要页面抽查、typecheck、build 和 dev 启动验证。

## 7. 本轮优点

本轮将项目状态从内容结构完成推进到上线前可检查状态，验证范围覆盖页面、内容、SEO、移动端和构建。

## 8. 本轮缺点与代价

当前仍未接入真实表单、线索存储、正式域名和线上部署环境。

移动端检查为关键页面抽查，不等同于完整设计走查。

## 9. 验证与结果

验证项包括：

- 全站低专业用词扫描
- 核心路由 HTTP 状态检查
- 移动端首页、文章页、服务页、诊断页、案例页抽查
- `npm run typecheck`
- `npm run build`
- `npm run dev`

## 10. 本轮结论

项目已具备本地可上线前状态：内容平台定位清晰，核心路由可访问，sitemap 与 robots 可用，构建可通过。

## 11. 下一轮建议

第一，确认正式域名并替换 `lib/seo.ts` 中的 `siteUrl`。

第二，确认部署平台后再处理环境变量、构建命令和线上缓存策略。

第三，若要做转化闭环，优先新增咨询表单与线索存储。
